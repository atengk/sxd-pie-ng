# 领域与架构文档规范 (Domain Docs)

本规范指导工程技能在探索和理解本工程代码库时，如何规范读取与维护领域知识文档。

## 探索前必读文件

- **根目录 `CONTEXT.md`**：阐述系统核心领域模型、概念定义与全局术语表。
- **`docs/adr/`**：架构决策记录（Architecture Decision Records）。在开展具体模块工作前，先阅读涉及该领域的 ADR。

若上述文档尚不存在，**请保持静默并直接继续执行**。不要将文档缺失视为阻塞，无需主动提议前置创建文档。当通过相关技能（如 `/domain-modeling`）实际推导并确立术语或架构决策时，再按需延迟创建。

## 目录结构（单上下文仓库）

本项目为标准单上下文结构（Single-Context）：

```text
/
├── CONTEXT.md          # 核心领域概念与全局统一术语表
├── docs/adr/           # 架构决策记录目录
│   └── 0001-xxx.md     # 架构决策文档
└── ...                 # 业务工程目录
```

## 遵循术语表定义

在命名领域概念（包括 Issue 标题、重构建议、设计推演、测试用例名称）时，必须严格使用 `CONTEXT.md` 中已定义的专业术语，避免引入近义词或混淆称谓。

若所需的概念尚未收录于术语表中，请注意辨别：是否正在引入本项目不适用的非标术语，或者领域模型存在确实的盲区（可记录并交由领域建模技能补充）。

## 架构决策冲突提示

若技术方案或重构推演与既有 ADR 决策发生冲突，必须显式标注并说明理由，严禁静默覆盖既有决策：
