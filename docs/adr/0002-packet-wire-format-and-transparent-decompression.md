# ADR-0002: 二进制封包线格式与透明 zlib 解压缩机制

## 决策背景

《神仙道》TCP 协议基于大端序二进制流传输，原 MFC 工具依赖特定外部动态库（`zlib.dll`）且针对大封包进行流压缩。若采用静态消息号映射维护压缩属性，官方接口升级或消息号漂移时极易引发协议解析崩溃。

## 架构决策

1. **基础包头定义**：采用标准 `[4 字节大端序长度 Length] + [2 字节大端序 Action ID]` 构成固定 6 字节包头。首部 4 字节长度字段包含其后紧随的 ActionID（2 字节）以及实际载荷长度，即 $\text{Length} = 2 + \text{len(Payload)}$。空载荷封包长度为 2。
2. **ActionID 编码数学映射**：16 位 ActionID 遵循 $\text{ActionID} = (\text{Action} \ll 8) \mid \text{Module}$，高字节为 Action 动作编号，低字节为 Module 模块编号（例如跨服登录 Module 94 Action 0 为 `0x005E`，副本扫荡 Module 25 Action 1 为 `0x0119`）。
3. **透明解压缩管道**：解码载荷字节流时，动态嗅探头部魔数（`0x78`，标准 zlib 压缩标识）。一旦命中魔数，由协议引擎在底层自动进行透明流式解压，解压完成后再交付上层业务路由器处理；未压缩封包原样透传。
4. **上层解耦**：业务层 Handler 仅面向解压后的原始载荷进行反序列化，彻底与通信层的压缩细节解耦。

## 结果影响

- **收益**：避免维护脆弱的消息号压缩特征表，协议解码器具备天然的自愈与向后兼容能力。
- **代价**：对于极罕见首字节恰好为 `0x78` 的非压缩载荷存在误判风险（将在反序列化层增加恢复与校验防御）。
